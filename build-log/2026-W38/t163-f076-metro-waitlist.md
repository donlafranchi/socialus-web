# T163 (Issue #77) — a person outside an open metro joins its waitlist

**Scenario:** F076 (`approved` 2026-09-14). **Depends on:** F059 criterion 6. **Blocks:** nothing.

## What shipped

**Migration `*_metro_waitlist.sql`** — schema, plus 296 rows of reference data.

- **The metro catalog.** `metro_polygons` now holds **every US metro**: 184 CSAs
  plus the 112 Metropolitan Statistical Areas belonging to no CSA. Generated by
  `scripts/build-metro-catalog.ts` from the U.S. Census **July 2023 CBSA
  delineation file** — a coverage claim needs an authority, not a memory.
  `geography` and `centroid` are now nullable: 295 of the 296 have no boundary
  and need none, because a person *picks* their metro (criterion 2 forbids IP,
  defaults and nearest-match). `resolve_home_metro` never matches a null
  polygon, so an unopened metro cannot become anyone's home metro — asserted,
  not assumed.
- **Per-metro thresholds and counts** on the same table: `creator_threshold`
  (50), `patron_threshold` (250), `creator_count`, `patron_count`, `is_open`.
  Thresholds change with an UPDATE — no migration, no deploy (criterion 11).
- **`public.metro_waitlist`** — one row per person, `member_id` **unique**.
  That single constraint is what makes joining idempotent (criterion 4) and
  makes changing metro a move rather than a duplicate (criterion 5): with one
  row per person, re-joining is an update and there is no second row to strand.
  RLS is SELECT-own-row only; who joined is never readable, rankable or
  displayable.
- **`metro.waitlist_join`** — maintains both counters in the same transaction
  as the row, so a move can never leave the old metro high and the new one
  empty.
- **`joinMetroWaitlistAction`**, `MetroWaitlistStep`, `MetroStandingDialog`, and
  the metro step wired into `OnboardingFlow`.

## The split never reaches the browser

The platform decides on 50 creators **and** 250 patrons, gated on creators; the
person reads one number against 300. The server action returns
`{ combined, target }` and a message — the per-role counts and thresholds do not
leave the server, so the popup cannot render them by accident. The action's test
asserts the exact key set rather than scanning for digits, because "50" and
"250" appear in an honest response for honest reasons.

`standingMessage` is scanned across every state it can produce for dates,
timelines, "soon", promises to open, and the words creator/patron — criterion 9
is a hard constraint, so it is tested as one rather than reviewed as copy.

## Judgment calls

**Everyone picks a metro, not only people outside an open one.** The app cannot
know who is outside without the inference criterion 2 forbids. So the step is
universal; picking the open metro skips the waitlist and the popup entirely.

**No progress bar.** Named in *Not this* beside leaderboards and referrals, and
a bar implies a rate of travel toward a destination — the same promise
criterion 9 forbids the words from making.

**A native `<select>` for 296 metros.** Typeahead, keyboard and screen-reader
behaviour for free; a custom combobox would be a new pattern and new bugs for
nothing. "Keep it simple" is the ticket's own constraint.

**Micropolitan areas excluded.** They are by definition not metros. That leaves
rural America picking a nearby metro — the same known hole `feed-metro.ts`
already names. Recorded, not silently dropped.

## Verification

**local Postgres, plus the running app.**

- Full suite **1847 passing**, 0 failing (1778 on `main` before; 69 new).
  `tsc` clean, `lint` unchanged from baseline, `build` passes,
  `check:action-layer` OK at 38 protected tables.
- **The four headline behaviours were exercised through the shipped handler
  against the real database**, not only against mocks:
  re-joining the same metro in the same role → `changed: false`, counts
  unchanged, still one row; moving to another metro → old metro back to zero,
  new metro at one, still one row; swapping role → creator 0 / patron 1, still
  one row.
- The whole flow was driven in a browser at 375×812: 297 options (296 metros
  plus a placeholder that is not a metro), nothing pre-selected, and the popup
  reading "Boise City-Mountain Home-Ontario, ID-OR / 1 of 300".
- Four tests in this change were wrong on first run and were fixed rather than
  accommodated. The one worth remembering: a scan for a `rank` column matched
  **"Bowling Green-Glasgow-Franklin, KY"** in the seed. Scanning 296 US place
  names for schema words finds Kentucky, so the scan is now scoped to the
  schema half of the file.
- **From-scratch apply is CI's `supabase db reset` job.** Not run locally —
  it would wipe a stack another session may be using.

## Known, and not fixed here

- `metro_polygons` is now a catalog of metros of which one has a polygon. The
  name no longer describes it. Renaming touches migration 031, both
  definer-hardening migrations, `resolve_home_metro`, `feed-metro.ts` and their
  tests — mechanical, and deliberately not bundled into a scenario ticket.
- `listFeedMetros` still returns every row, which is now 296 rather than 1. No
  surface change today (nothing else is open), but the Browse switcher should
  scope to `is_open` before a second metro opens.
- Onboarding still assigns a **default home *place*** server-side and unseen
  (`DEFAULT_HOME_PLACE_ID`). That is a place, not a metro, so F076 criterion 2
  is untouched — but it sits close enough to the rule to be worth naming.
