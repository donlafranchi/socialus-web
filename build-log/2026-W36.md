Not a true overlapping crossfade — that needs both panes painted at once, which means either mounting Mapbox on every Explore visit or sizing a stacked container to the list's full scroll height. **Caught by M3 — an invisible focus ring on two tablists.** The selected tab in this toggle *and* in T114's kind pills had no visible keyboard focus indicator. Neither component set `outline-color`, so it fell to the UA default `currentColor` — which on a selected pill is white, drawn against the white page. Tabbing onto the selected kind pill showed nothing at all.

The fix sets `outline-[var(--color-accent)]` **unconditionally**, with only `outline` and `outline-offset-2` under `focus-visible:`. Setting the colour outside the state variant means it appears in the computed style whether or not the element is focused, so the next regression is catchable by a unit test and a screenshot instead of only by someone pressing Tab. Confirmed under a real keyboard Tab: `outline: 2px solid rgb(15, 171, 142)` at 2px offset on the selected tab of both rows. The `KindFilterPills` change is one line in a component this ticket does not otherwise own — leaving a known invisible ring on the adjacent tablist of the surface under M3 review was the worse option.

**Worth recording about the diagnosis.** The first attempt put the colour under `focus-visible:` like the width and offset. `getComputedStyle` then reported `rgb(255,255,255)` even with `:focus-visible` matching and the offset correctly applied, and the compiled CSS *did* contain `.focus-visible\:outline-\[var\(--color-accent\)\]:focus-visible { outline-color: var(--color-accent) }`. Rather than keep bisecting a state-dependent computed value, moving the colour out of the variant made it directly observable — and correct. A property whose UA default is `currentColor` is a bad thing to set only under a pseudo-class.

**Caught by the tests.** A string replacement while adding the ring dropped the `before:*` classes that grow each kind pill's hit area to the full 44px row — T114's own hit-area test went red immediately and the classes went back.

## T118 — The Item card always renders a media block

Decision A (`planning/backlog/decision-item-card-media.md`, ratified 2026-09-04). No scenario and no F-number — this originates in a PM design decision, so `design-language.md` § Card was amended first and the ticket cites the amended recipe. Presentational only; no schema, no data field, no new query.

**The diagnosis, confirmed before building.** `ItemFeedCard` gated its 4:3 media block on `photo_url`. `grep -rn "photo_url" supabase/seeds/*.sql` returns exactly one line — an `item_products` insert whose `photo_urls` is `array[]::text[]` in every row. No seeded Item has ever had a photo, so the block had never rendered on any surface, and all 16 published Items drew as unstyled text on white. There was no richer card to restore; this is new design.

- **The media block is now unconditional.** Photo → `object-cover`, no overlays. No photo → a neutral kind field: `--color-surface` ground, centred lucide glyph at 28px / 1.5 stroke in `--color-fg-muted`, nothing else.
- **Seven kinds, seven glyphs**, fixed in the DLS so no surface picks its own: `CalendarDays` / `Package` / `Handshake` / `Lightbulb` / `Gift` / `HandHeart` / `Flag`. `lucide-react` was already a dependency in eleven components; no new art and no new package.
- **No colour in the placeholder.** Not a per-kind palette, not a tint, not an emoji. The remembered `VendorCard` emoji-on-surface treatment was considered and rejected on three counts: its vocabulary was the retired vendor `CATEGORIES` (`bread`, `produce`), emoji are full-colour platform art the DLS does not control, and Principle 1 spends its accent budget elsewhere. The retired no-photo bullet's colour prohibition survives the override and is what constrains this.
- **The kind chip is gone.** `.chip` is `px-3.5 py-2 text-sm`; the old `text-[11px]` override shrank the font and not the padding, so it rendered ~32px tall above a 14px title — the heaviest element on the card, for a label that is not interactive. Replaced by the 11px/600 uppercase muted editorial label the DLS already specified for no-photo cards, now used on both media states so photo and placeholder cards have identical text zones.
- **The card has an edge and fills its cell.** `1px --color-border` at rest (Principle 6 prefers hairlines; the old no-border rule assumed a photo supplying the edge). `flex h-full flex-col` with the text zone growing, so rows stay flush regardless of title wrap. **No width class and no column-count assumption** — the component renders in three grids at 2/3, 2/3, and 2/3/4 columns today and the merged Home surface may use a fourth.
- **Tokens replaced hardcodes.** `text-neutral-900/600/500` → `--color-fg` / `--color-fg-muted`. The original violated web/CLAUDE.md § Design System; the rewrite fixes it in passing.

**Chrome untouched, deliberately.** No edit to the search bar, filter icon, bottom sheet, kind-pill row, or list/map toggle. Those land on the merged Home surface per `decision-surfaces.md`; rebuilding them now would rebuild them twice.

**M2 code review** found one issue — a redundant `overflow-hidden` already applied by `.card`. Removed before commit. Checked and clear: no other component or eval queries the removed `.chip` class or asserts the media block's absence; the glyph is `aria-hidden` with the kind carried as text so nothing is lost to AT; `h-full` resolves in all three grids (in `ExplorePage` the stretched `<li>` is the containing block, elsewhere the card is the grid child directly).

## T119 — Canonical Item URLs and browsable-kind withholding

Scenario F054, review `review-F054.md` (PROCEED, three binding notes). Fixes the 404 rate the card diagnosis surfaced: 9 of 16 seeded Items opened nothing.

**Three causes, not two.** The decision stub named two — Group-filed rows got a `/m/` link the resolvers reject (4 rows), and four kinds have no detail page (5 rows). A third was found during build and is the one that mattered most for v1: **attribution on the Group path read `items.brand_label`, which is populated only from `group_businesses.display_name`.** A gathering filed under a non-business Group has it null and every resolver returned `null` — so the seeded Repair Cafe 404'd *twice*, once for the link shape and again at the resolver. Group events are v1 scope and every one of them is filed under a non-business Group, so this would have taken the whole workstream down. Fixed uniformly across all three resolvers: `brand_label ?? groups.name`.

**The Group routes already existed.** `/p/[…place]/g/<group>/{p,s,e}/<item>` has dispatched since T079/T082/T083. Nothing needed building — `itemHref` simply never emitted them. The stub framed this as *build the place-path* vs *redirect from `/m/`*; reading the code retired both framings.

**The place segments were never load-bearing, and that is why they had to be built from real data.** Every resolver keys off the globally-unique Group slug and ignores the place path — the F038 fixture says so in a comment. So nothing forces those segments to be true, which means a wrong one would render a perfectly working page while publishing a false address. The path is derived live through `groups.anchor_location_id → locations.place_id → places`, walking `parent_id` and skipping the county tier, and it round-trips: `place_url_path` verified against the CA seed returns `ca/west-sacramento` (Yolo skipped) and `ca/sacramento/curtis-park`, exactly what `resolvePlacePath` resolves back.

**Derived live, not denormalized into the MV** — deliberately. The view refreshes on `item.published` only, so a Place rename would leave every affected Item carrying a stale path until some unrelated Item happened to publish. One extra batched RPC per browse buys a path that is always current. Migration `037` adds two `security invoker` functions (`place_url_path`, `group_url_prefixes`) over tables that are already anon-readable; the MV and the three feed RPCs are untouched.

**The four kinds are withheld, not stubbed.** A dead-end page for an Ask misrepresents the product — an Ask exists to be answered, and the response substrate has no handler for any kind. A broken link reads as unfinished; a page that does nothing reads as *this is the feature*. Withholding is also the cheaper reversal: one entry in `BROWSABLE_KINDS`. The cost is named rather than hidden — the seeded feed goes from 16 Items to 11.

**Three shipped filter pills came off with them.** Not in the ticket; predicted by the review's sibling check. T114's row offered Ideas / Offers / Asks, which after this change could never return a result — three controls that always render the empty state, which reads as a broken filter rather than an unbuilt feature. `KIND_FILTERS` is now derived from `BROWSABLE_KINDS` so the two cannot drift apart again.

**M2 code review** found two issues, both fixed before commit. `fetchExploreItems` applied the browsable constraint only on the All path, relying on `parseKindParam` upstream to reject a withheld `?kind=` — the constraint is now unconditional so an exported function cannot surface a 404ing kind regardless of caller. And `place_url_path`'s ancestor walk was unbounded; `places.parent_id` has no cycle constraint and this runs on every browse, so a depth guard now makes an accidental cycle degrade to a wrong path rather than hang the feed.

**Verified against production data before shipping:** all four Group-filed Items resolve to real place paths (`/p/tgp/the-good-place/orchard-hill/g/the-good-loaf/…`, `/p/tgp/the-good-place/pond-side/g/repair-cafe-regulars/e/…`), and every Location in the showcase seed carries a `place_id`, so no Group falls back.

Tests: 677 passed, 1 failed — `EmailFirstSignup`, red on `main` before this branch and unchanged by it. Build clean; lint identical to `main`'s baseline (17 errors, one fewer warning); typecheck adds no new errors. New coverage: `item-url.test.ts` and `group-prefixes.test.ts` (both new files — the URL helper had none), plus the fallback path, the withheld set, and the Group-name attribution in each of the three resolvers.

**Deploy is not complete at merge.** Migration `037` must be applied to production by hand — this project has no migration runner yet. Until it is, every Group-filed link falls back to the Member path and those four 404s persist.

## T132 — Founder membership role branches by Group kind

Scenario F060 (someone starts something without opening a shop). Resolves the role-vocabulary divergence between `groups.md` and code recorded in `planning/stage-ledger/F060.md` — the spec was already right; `group.create` had a stale-comment bug hardcoding `role='owner'` for every kind. No schema change; both `owner` and `steward` already exist in `group_memberships.role`.

- New `managingRoleForKind(kind)` in `src/actions/group/constants.ts` — `'owner'` for `business`, `'steward'` for every other kind. Single write-path fix point; two independent readers (`member_has_standing_presence`, `acquisition-prompt.ts`'s qualifying probe) already branched this way in SQL and needed no change.
- `group/create.ts`'s founder-membership insert and its `group.member_joined` event payload both derive the role from the same call, once.

**Caught by M2 code review:** `group/update-draft.ts`'s own owner-only authorization gate hardcoded `role = 'owner'` unconditionally, with no kind branch — left unfixed, this would have locked every non-business founder out of editing their own draft Group the moment they correctly received `role='steward'`. Fixed in the same pass via the same `managingRoleForKind()`, with its own regression test. A follow-up sweep confirmed no other action handler, RLS policy, or UI affordance gates on a bare `role = 'owner'` without already scoping to `kind='business'` explicitly.

**A second, dormant bug's fix rides along.** `member.md`'s prompt-on-acquisition feature (Ratified 2026-06-03) already fires on "a business-kind membership OR a steward role in any Group" — but since no non-business founder had ever actually received `'steward'`, that half of the feature silently never fired. It now does, correctly. Not new scope — see `development/deviations/T132.md`.

**Ticket-scoping note.** T132's own acceptance criteria predicted two eval fixtures needed a `role: 'owner'` → `'steward'` correction; both turned out to already be correct (they belonged to business-kind fixtures). No fixture changes were made.

Tests: 36 vitest GREEN (`constants.test.ts` 6 new, `actions-t070.test.ts` updated for both `group.create` and `group.update_draft`). tsc clean on touched files.
